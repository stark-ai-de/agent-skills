# Security Contract

## Credentials

| Credential                  | Holder                        | Consumers                                               | Rollback  |
| --------------------------- | ----------------------------- | ------------------------------------------------------- | --------- |
| `HETZNER_INFERENCE_API_KEY` | Protected provider file       | Owned gateway only                                      | Preserved |
| `LITELLM_MASTER_KEY`        | Separate protected local file | Codex helper, Claude launcher, explicitly guided Cursor | Preserved |

The local `sk-` value is cryptographically random and administrative. Without LiteLLM's database-backed virtual-key system it is not scoped, least-privilege, budget-limited, or revocable independently of rotation.

Secret values are accepted only from bounded stdin, protected files, or secure random generation. Initial setup preserves protected credential files only when their exact non-secret observations are bound to an unchanged completed rollback receipt; arbitrary pre-existing credentials are never adopted. Under the mutation lock, the receipt is also verified with a gateway-keyed HMAC of the provider credential. This pair-continuity proof detects same-size content replacement without storing a raw-secret hash or making offline workflows read either secret. Newly written and preserved values are validated again immediately before apply or process start. They are rejected when empty, oversized, multiline, NUL-containing, or whitespace-altered. The gateway credential must additionally match the generated `sk-` plus 43-character Base64url format at every consumer. Reads bind a freshly classified WSL path and the pre-open protected named identity to an open handle, recheck topology per permission segment and again after awaited hooks immediately before named `lstat`, `chmod`, ACL, or `open` operations, then compare two exact reads plus size and nanosecond modification time before returning. Installed credential and Claude helpers immutably bind both complete managed roots and own that check without relying on the setup parent. Startup reconfirms the credential-pair continuity proof, and the installed runner rereads both protected values, compares their exact in-memory digests, and refreshes the complete root/credential/executable boundary immediately before spawning LiteLLM.

## Filesystem

- POSIX managed directories are current-user-owned `0700`; secret files are `0600`.
- Windows state and secrets stay under `%LOCALAPPDATA%`. Managed directories and protected files remove inherited/broad grants and verify the owner plus normalized current-user SID ACL.
- All platforms reject symlink/reparse path segments, special files, unexpected nested entries, and path escapes.
- External client parents are never implicitly created or owned. A selected Codex adapter requires `${CODEX_HOME}` to be disjoint from both managed roots before target I/O under conservative host comparison; macOS Unicode-normalizes and uses conservative Unicode case-insensitive collation, including non-simple folds, before containment checks. The parent must be a pre-existing protected directory whose filesystem identity and POSIX owner/mode or exact Windows owner, protected-inheritance flag, current-user ACE set, inheritance/propagation flags, and effective rights are bound by every existing-installation plan, including lifecycle and rotation, and revalidated against the opened parent before every read, publish, claim, cleanup, rollback, resumed action, and terminal check. `InheritOnly` ACEs cannot contribute rights on the protected object. Status, diagnose, check, planning, verification, apply, and rollback reject Windows UNC/device syntax before any external-target filesystem call and query the underlying drive type; `%USERPROFILE%\.codex` outside `%LOCALAPPDATA%` is accepted only on a `Fixed` local volume without reparse redirects and with sufficient current-user mutation rights, while mapped network drives are rejected. An absent, overlapping, or invalid external parent blocks child inspection even without a manifest. Rollback removes only the owned profile file and leaves the parent.
- Writes retain a verified parent-directory handle, create an exclusive empty same-directory temp, verify its identity and restricted protection before writing data, `fsync`, and publish with an exclusive no-replace operation while the opened and named parent identities still match. Linux child operations resolve through the retained descriptor; every platform rechecks the handle identity and symlink/junction/reparse state at each boundary. Parent rename/replacement or temp replacement fails closed. Replacements first quarantine and reverify the exact expected inode and content; publication fails if the original name reappears.
- Replacements are allowed only for paths attributed to the manifest and current plan. Only non-secret files receive backups; backup storage is current-user-only `0600`, and later status/proof revalidates its hash, mode, owner, or Windows ACL. Restoration reads the backup through a verified handle, claims the exact transaction target, and publishes without replacing a concurrent writer. Destructive cleanup and rollback first atomically claim the path into an unpredictable same-directory quarantine name, reverify object identity plus hash/tree/token, and synchronously delete the final verified claim with no intervening JavaScript yield. For the external non-secret Codex profile, the verified bytes are also published under an unpredictable protected managed-state quarantine name before post-claim hooks; success removes that copy by identity and hash, while failure retains its reachable path for CLI and offline status even if `${CODEX_HOME}` was renamed. A replacement at the original name survives; a mismatched claim observed at a verification boundary remains quarantined for manual recovery. After ACL verification, Windows noop planning compares type/hash and ignores synthetic POSIX mode bits. Every idempotent apply or completed-rollback result repeats the external-parent proof after lock release and has no later asynchronous boundary before return.

The asynchronous orchestrator and installed runner share the canonical path-segmentation and filesystem-identity primitives from `protected-file.mjs`. Their atomic-publication control flows intentionally remain separate because the installed runner must remain dependency-free and synchronous once its pre-publication proof completes. The opened temporary identity is carried into Windows normalization; every awaited ACL step is followed by a fresh segment scan, a real local-containment calculation, and a named/open identity comparison before any subsequent named mutation. The installed receipt helper performs normalization and final ACL inspection in one bounded PowerShell process. Windows root ACL proofs deduplicate equal roots and inspect distinct roots concurrently so polling and receipt timers remain responsive. Behavioral parity tests require both implementations to preserve create, same-content/new-inode rejection, identity-bound replace, post-claim replacement survival, and concurrent no-replace semantics.

The operating-system account is the trust boundary. Managed state is protected against concurrent skill instances, stale or accidental changes, and redirections observable at the documented checkpoints. It is not a sandbox against hostile code already running as the same user: such code can bypass per-user permissions and deliberately replace a quarantine pathname in the final operating-system syscall window. Suspected same-account compromise requires stopping the helper and recovering outside it.

Do not copy credentials across Windows and WSL. Each OS boundary owns its own mutable state. WSL derives DrvFs boundaries from `/proc/self/mountinfo`, including custom and manual mounts, and rereads and parses that source at every classification boundary. The parser requires structurally complete records and a valid root mount, so empty, malformed, truncated, rootless, missing, or unreadable metadata blocks the operation. It resolves local aliases without following them into Windows and rejects Windows-mounted home, XDG, Codex, PATH, and selected executable paths before profile I/O or version execution. The installed Claude launcher binds OS-derived home, temp, and PATH defaults and independently rejects every forwarded search namespace or path-valued helper plus each explicit or effective mutable-state namespace—including `HOME/.claude` and default XDG roots—before reading its local gateway key and again immediately before spawn. The runner applies the same explicit/effective home, temp, and PATH checks before reading either credential and before spawning LiteLLM. A DrvFS mount nested anywhere in one of those namespaces, either complete managed namespace, or the external profile blocks child I/O. Managed namespaces are reclassified after awaited plan checkpoints and inside lock/manifest/storage entrypoints. Persisted executables, standalone credential reads and client spawns, runner receipt publications, and stop claims are reclassified against freshly read topology during status, check, plan validation, apply (including idempotent no-op), spawn, long-lived runner operation, and client-evidence verification.

## Plans and locks

A mutation accepts no interactive improvisation. It requires an unexpired plan whose digest, schema, skill version, host, roots, fixed runtime paths, exact target set, process action, credential actions, executable paths/versions/content hashes, approval disclosures, evidence hashes, and observed state validate locally. `--approve` must equal its `planId`. Rehashing an edited plan cannot confer credential ownership: setup reopens and verifies the completed rollback receipt and its continuity proof under the mutation lock before any setup action.

Each successful `mkdir` is the exclusive claim for that new directory. On WSL, traversal refreshes the owned-namespace classification before its target I/O; apply repeats it after asynchronous plan validation, and lock acquisition performs the check internally before bootstrap or exclusive publication. On POSIX, an already-verifiable `0700` result is never chmoded afterward; a more restrictive umask result may be normalized only while every contender's read-only verification still blocks. Existing roots are verified read-only and are never chmoded or ACL-repaired before ownership. The mutation lock itself is published directly with exclusive creation, so a losing writer creates no temp, changes no root metadata, and returns `mutation_locked`. The winner retains the opened identity-bound proof and may finish Windows protection of a newly created root only while that lock is held. Failed direct publication snapshots the actual bounded bytes through the retained handle; any completed write must still equal the intended bytes, and final identity, size, time, and content revalidation runs synchronously through deletion while that handle remains open. A mismatch preserves the residual lock. Every internal temp creation/write, target claim/publication, quarantine deletion, process request publication, process spawn, and release revalidates the named path, open identity, current WSL namespace, and originally published document bytes. Release passes the original identity and byte hash into the removal claim, rechecks both after every pre-remove boundary, keeps the retained proof open through final verification, and issues the delete synchronously without another JavaScript turn. A replacement observable at any verification boundary is preserved; after POSIX deletion the retained lock proof must also be detached from its directory entry. A missing, modified, or replaced lock returns `lock_ownership_lost` and blocks further cleanup rather than continuing concurrently. If release also fails while a primary workflow error is active, only a stable secondary code is attached; the primary conflict and quarantine recovery path remain authoritative. An unverifiable process receipt during failure handling preserves the transaction for manual recovery instead of treating runner termination alone as cleanup authority. Bounded runtime, permission, and version commands wait for `close`; timeout sends TERM, escalates to KILL, and returns a conflict with cleanup disabled if closure remains unconfirmed.

## Process lifecycle

The gateway is fixed to loopback port `4000`. Every existing receipt is identity-checked before startup. A stale non-terminal or mismatched receipt blocks instead of being overwritten; only a matching terminal receipt permits a new start. Port occupation without a fresh complete owned identity also blocks. New startup reaches `ready` only after repeated authenticated `/v1/models` checks return the configured alias. A receipt PID is informational; it is never sufficient authority.

The runner owns the exact spawned LiteLLM handle. Start binds protected identity/permission observations for both managed roots, and the installed runner revalidates them before every receipt or stop operation; equal roots are checked once per proof, distinct Windows roots are inspected concurrently, and ACL inspection uses bounded asynchronous children so the production 250-ms stop watcher and receipt queue stay responsive. Its final asynchronous root and child-environment proof precedes the final protected credential-pair reread; the subsequent pair comparison, synchronous recheck, and spawn have no awaited or injectable boundary. It never creates, chmods, or ACL-repairs a missing, replaced, or drifted parent. Every published receipt transition is current-user-only, parent-directory-bound, and compare-and-swap bound to the prior file identity and content, with exclusive no-replace publication and a normalized Windows ACL applied and verified in one process only on the empty temp before receipt data is written. Heartbeat publication is single-flight: timer ticks coalesce, lifecycle state is rechecked when the operation dequeues and after asynchronous proof, timestamps are created at execution, and any pending readiness is canceled when failure or stopping wins. Stop clears timers and starts exact-child termination immediately. The protected request publishes one absolute end-to-end 15-second deadline shared by caller and runner across request publication, every caller receipt read and terminal proof, polling, ACL child execution plus confirmed escalation, the shared TERM/KILL wait, claim cleanup, and the mandatory terminal receipt. Fifteen equal units allocate three to publication, four to runner detection/protection/claim, two to termination, two to terminal publication, two to exact-claim cleanup, and two to caller proofs. These separate cutoffs keep Windows ACL execution feasible without letting a late step consume a downstream interval. When readiness is already in flight, it is canceled and the terminal publication directly supersedes it instead of queuing another intermediate `stopping` write; otherwise the distinct closed-schema stopping receipt remains observable. Root or topology drift clears all timers and terminates/awaits the exact child before touching a replacement target. A write failure at readiness, heartbeat, stopping, or terminal state has the same termination requirement; queued readiness rechecks failure state and cannot publish afterward. A child `error` event is retained as failure context but does not prove termination without `exit`, `close`, or terminal child state. Once termination is confirmed, the runner publishes `stopped` or `failed` with the exact request timestamps, claim name, and claim hash, then removes the retained claim as the completion commit. Every exit before an authorized stop—including code `0` or a signal—is failed. Status and lifecycle operations validate the complete receipt structure and bind it to the manifest, runner, child, executable, arguments, configuration, port, and start time. A caller may observe a terminal receipt before cleanup finishes, but it cannot authorize rotation, rollback, or any follow-on action until the bound claim is absent and the protected receipt, full manifest/file identity, and request-absence proofs pass within the shared deadline. Both exact `stopped` and exact `failed` complete that contract, and the result preserves the distinction. A check independently requires a fresh `ready` receipt and revalidates the immutable gateway/process boundary after the administrative-key read, immediately before every gateway request, after every gateway or client proof, and once more before publishing its report. Expected heartbeat-only receipt changes are allowed, and the final receipt digest is published; a provider delay or actual concurrent lifecycle change blocks gateway-key use and client-evidence promotion. Immediately before spawn, start rehashes the Node executable and re-inventories the owned runtime. Stop requires that fresh token-bound identity. A missing receipt is a no-op only when the manifest records exactly `not-started` or `not-running` and no process identity; otherwise it blocks. The parent writes a protected, closed-schema token-bound stop request containing the shared deadline; immediately before a synchronous claim, the runner re-verifies its bound identity/content and current-user-only POSIX owner/mode or Windows ACL. A concurrent request replacement survives but blocks lifecycle completion and appears as process drift until resolved. Failed setup startup may clean transaction state only after the exact runner is confirmed terminal and a matching terminal receipt plus claim-absence proof independently prove LiteLLM-child termination and publication completion; direct runner termination without those proofs preserves runtime, configuration, and credentials under a stable manual-recovery conflict. A post-start manifest failure triggers an exact-token compensating stop. If it encounters `stopping`, it validates and joins only the protected existing claim and embedded absolute deadline; it never creates a fresh window. Failed compensation preserves state for manual recovery and retains its stable conflict code through the CLI boundary.

The exact request window has fifteen equal budget units grouped into non-overlapping intervals: publication gets three, runner detection/protection/claim four, termination two, terminal publication two, exact-claim cleanup two, and caller proofs two. Receipt replacement has a deliberate claim-to-link interval in which the published name is absent. Only an already committed or joined stop treats absence, `ENOENT`, or an invalid-receipt read immediately reconfirmed absent as retryable inside the original deadline; any present malformed or mismatched receipt fails closed. The protected terminal receipt binds the request timestamps plus claim name and hash. A caller may observe that receipt during cleanup, but it accepts completion only after the bound claim is absent and the terminal identity and request-absence proofs pass. Every installed ACL child retains its process handle until `close`, escalates from TERM to KILL within its interval, and fails closed if close cannot be confirmed.

## Redaction and logging

LiteLLM body logging and verbose environment diagnostics are disabled. The helper returns stable error codes and redacted messages without internal error details; when a failed atomic claim must be recovered, the only additional error field is its sanitized quarantine path. Probe capture redacts raw, Base64, Base64url, and hexadecimal forms of credentials plus authorization-header patterns. Credential-bearing checks conservatively reject Node environment-proxy mode before reading a credential, including quoted `NODE_OPTIONS` spellings, so loopback and provider bearer headers cannot be redirected through inherited proxy configuration. Every HTTP path bounds or cancels the response body and clears its timeout, including non-OK and bodyless streaming responses. Failed probes remain present in the JSON report and make the entry point exit with external-failure code `6`.

Manifests, process receipts, rollback journals/receipts, and client evidence use closed root and nested schemas. They contain credential paths, purpose, mode, bounded size/mtime metadata, and preservation policy only—never values or value-derived hashes. Unknown or status-inconsistent fields fail closed, and diagnosis reports only sanitized file metadata rather than document contents. Before sharing a plan, manifest, receipt, check report, or log, scan it again for secret material and private paths.

On Windows, approved `.cmd` and `.bat` client shims run only through the machine-local `System32\\cmd.exe` with delayed expansion disabled, verbatim arguments, and command-metacharacter escaping. Direct spawn remains the rule for native executables.

## Rotation and rollback

Rotation stops the owned process first and atomically replaces only the selected credential. The selected target may have a known permission/ACL drift: its exact type and content stay hash-bound until replacement, its pre-write permission failure is deferred, and the replacement must pass the full protection check. No automatic old-secret backup is written. All prior live/client evidence is invalidated.

Rollback persists a protected in-progress journal before deletion, including the credential-pair continuity proof, then freshly verifies each remaining artifact and backup hash plus mode/owner/ACL, every external-parent identity/protection snapshot, runtime tree, manifest, credential observation, credential content proof, and process state before every action and resumed action. External deletions carry that planned parent proof into the opened-directory claim and recheck it at terminal absence validation, so a replacement directory cannot produce false success or receive deletion. Missing previously owned targets are retryable only under that exact journal and approved plan; modified targets block. The manifest is removed last and the journal is atomically replaced by a completed receipt. Credentials are preserved unless a separate future workflow and approval explicitly authorize deletion.
