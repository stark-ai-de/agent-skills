# Architecture

## Boundary

```text
Codex CLI       -- Responses ---------+
Claude Code     -- Messages ----------+--> LiteLLM 127.0.0.1:4000 --> Hetzner Chat Completions
Cursor standard -- guided BYOK -------+
```

Hetzner Inference is experimental. The provider surface is `https://inference.hetzner.com/api/v1`; `/models` is authoritative for current model IDs and `/chat/completions` is the upstream generation contract. Recheck the [official Hetzner documentation](https://docs.hetzner.com/general/company-and-policy/experiments/inference/) before changing this integration.

LiteLLM owns protocol adaptation. The skill owns the exact isolated install, loopback configuration, client sidecars, credentials, lifecycle receipt, plans, evidence, and rollback. It does not implement a protocol server.

## Fixed baseline

- Gateway: `127.0.0.1:4000`; no fallback port and no non-loopback binding.
- Alias: `hetzner-default`.
- Upstream route: `openai/<live-model-id>` with `use_chat_completions_api: true`. Model-scoped `additional_drop_params: ["reasoning_effort"]` removes the unsupported OpenAI reasoning-effort hint used by Codex; tools remain intact and global `drop_params` stays false. This does not configure the provider model's own reasoning behavior.
- Messages translation: the owned single-provider gateway sets `litellm_settings.use_chat_completions_url_for_anthropic_messages: true`, selecting the official Messages-to-Chat adapter. This avoids a 1.101.0 Responses-to-Messages conversion that loses visible message objects. The global switch is never applied to a shared remote instance by this skill.
- Runtime: per-user virtual environment with `litellm[proxy]==1.101.0`.
- Python: `>=3.10,<3.15` for this reviewed pin.
- Logging: request bodies and verbose environment diagnostics disabled.
- Authentication: separate provider token and administrative local master key.

The pin was reviewed against the [LiteLLM PyPI release metadata](https://pypi.org/project/litellm/) on 2026-08-26. Re-review the pin, Python range, generated YAML, probes, and client contracts together before updating it.

## Host roots

| Host          | Configuration                                                  | State                                                              |
| ------------- | -------------------------------------------------------------- | ------------------------------------------------------------------ |
| Linux and WSL | `${XDG_CONFIG_HOME:-$HOME/.config}/stark-ai/hetzner-inference` | `${XDG_STATE_HOME:-$HOME/.local/state}/stark-ai/hetzner-inference` |
| macOS         | `~/Library/Application Support/stark-ai/hetzner-inference`     | Same root                                                          |
| Windows       | `%LOCALAPPDATA%\stark-ai\hetzner-inference`                    | Same root                                                          |

`${CODEX_HOME}/hetzner.config.toml` is the only client file outside these roots. It is an additive profile overlay, not a replacement for base Codex configuration. `${CODEX_HOME}` must be disjoint from both managed roots under conservative host comparison and already exist with verified current-user protection; macOS Unicode-normalizes and applies conservative Unicode case-insensitive collation, including non-simple folds, before containment comparison, and overlap is rejected before target I/O. Planning records its filesystem identity and protection snapshot, every publication/claim/removal revalidates both against the opened parent, atomic publication may not create it, and rollback leaves that external parent untouched. An absent or invalid parent blocks child inspection, including no-manifest status and diagnosis. Windows keeps managed roots under `%LOCALAPPDATA%`, rejects UNC/device syntax before external-target I/O, rejects mapped network drives by `DriveType`, and accepts the normal `%USERPROFILE%\.codex` external parent only on a `Fixed` local volume when it has no reparse segment and its exact owner, protected-inheritance flag, current-user ACEs, inheritance/propagation flags, and effective mutation rights on the directory pass verification. `InheritOnly` ACE rights do not apply to that directory.

WSL is a distinct host. Run its gateway and clients inside the same distribution. The host adapter rereads and parses the kernel mount table at every classification boundary for DrvFs volumes, including custom automount and manual mount points, and resolves local symlink aliases without following them into the Windows target. A table is trusted only when every record is structurally complete and it contains a valid root mount; empty, malformed, truncated, rootless, or unreadable metadata fails closed. Windows-mounted home, XDG, Codex, PATH, and selected executable paths are rejected before profile I/O or version execution; any DrvFs mount nested inside either the lexical or fully resolved owned configuration/state namespace or placed at the external Codex profile blocks child I/O. Managed storage is reclassified after awaited plan checkpoints and inside lock and manifest entrypoints. Installed credential/client helpers and the long-lived runner carry immutable bindings for both complete roots plus the same dependency-free parser; the Claude launcher also validates every forwarded home, Claude, XDG, and temporary mutable-state root before its key read and immediately before spawn. Synchronous permission scans classify every segment and immediately reclassify before named `lstat`, `chmod`, ACL, and `open` operations, while asynchronous scans repeat every segment, local-containment, and named-identity proof after awaited checkpoints. The runner also classifies its bound Node executable and script before identity reads. Status, check, plan validation, idempotent and mutating apply, runner spawn/operation, and client-evidence verification therefore use freshly read topology. A cross-boundary flag requires fresh reachability evidence and then fails closed because this baseline cannot own configuration in another OS boundary.

## Ownership transaction

1. `diagnose`, `plan`, and `status` inspect metadata offline.
2. Provider discovery is a separate, explicitly approved read-only network action.
3. `plan` binds current paths, file metadata and hashes, executable paths/versions/content hashes, evidence hashes, desired outputs, process action, approvals, expiry, and host boundary into `planId`. Offline planning may propose reuse only when credential observations still match a completed rollback receipt.
4. A mutation creates missing POSIX directories with an exclusive `mkdir`; an already-verifiable `0700` result receives no later chmod, while a more restrictive result blocks every contender until its creator normalizes it. Existing roots are read-only until direct exclusive lock publication, and only the lock winner may finish Windows root protection. The winner retains its open lock identity, validates the plan shape and exact approval, reopens the rollback receipt when setup would preserve credentials, verifies its secret-safe pair-continuity proof, revalidates sources/evidence/executable content and versions/state, then proves the same lock path, inode, and originally published document bytes again at every internal create/write/publish/claim/delete or process boundary and before release. Failed publication cleanup binds the actual bytes through that retained handle and preserves any in-place change. Missing, modified, or replaced lock state fails closed without further cleanup.
5. Atomic writes bind the verified parent-directory identity before creating an unpredictable same-directory temporary file. The empty temp identity and protection are verified before data is written; publication and cleanup retain the directory handle, revalidate the opened and named identities at every boundary, and use exclusive no-replace operations. Linux child operations resolve through the retained descriptor. A parent rename, symlink, junction, reparse replacement, or temp replacement fails closed. Replacements first claim and reverify the exact prior file, then publish only while the original name remains absent. Replaced manifest-owned non-secret artifacts receive hash-bound, current-user-only `0600` backups whose hash and protection metadata are revalidated.
6. The final closed-schema manifest records runtime inventory, resolved packages, artifact hashes/modes, credential metadata without hashes or values, process identity, evidence invalidation, and rollback actions. Unknown fields fail closed and are never echoed by diagnosis.
7. Credential reads bind the pre-open protected path to the opened handle, revalidate the named path and protection while that handle remains open, and compare two exact reads before returning an in-memory value. The runner reconfirms both values against their in-memory digests immediately before passing them to LiteLLM. Failed setup/add-client/repair work restores only hash-matching files read through verified handles from its own backups and removes only exact values/files created in that transaction. Restoration claims the exact transaction target and uses no-replace publication, so a post-claim concurrent replacement survives and both the backup and rejected claim remain available. Every cleanup or rollback deletion first atomically renames the identity-bound target to an unpredictable same-directory quarantine path, revalidates its hash/tree/token there, rechecks lock ownership at the claim and delete boundaries, and deletes only that claim; concurrent replacements at the original path survive. An external Codex-profile claim additionally publishes its verified bytes to a protected managed-state recovery name before an injectable boundary; successful cleanup removes both claims. Failure exposes a CLI/status recovery locator only while the managed copy still matches its recorded identity, hash, mode or ACL. A missing, same-content replacement, or protection-unverifiable recovery copy fails closed without a false preserved-path claim. Bounded child commands settle only after `close`, with TERM-to-KILL escalation; an unconfirmed close makes cleanup unsafe and preserves the transaction for manual recovery. Windows noops compare type/hash after ACL verification and do not interpret synthetic POSIX mode bits; every existing-installation plan binds all owned external parents, and every idempotent result revalidates them after lock release immediately before return.

Unexpected nested entries, symlinks, reparse redirects, broadened permissions, changed targets, stale plans, and concurrent writers fail closed.

## Process identity

The installed runner owns the LiteLLM child handle. Its current-user-only receipt records a random process token, runner and child PIDs, runner executable/script, gateway executable, arguments digest, configuration path/hash, host, port, start time, and heartbeat. Start passes protected identity/permission observations for both managed roots; the installed artifact independently binds those exact root paths, Node executable, and script. Its final asynchronous root and child-environment proof runs before the final protected credential-pair reread, after which pair comparison, synchronous recheck, and spawn contain no awaited or injectable boundary. Every published transition verifies the unchanged root observations, refreshes the WSL storage boundary, claims the exact prior receipt identity and content, then publishes with an exclusive no-replace operation; the same proof precedes every stop poll and claim. The published receipt name is therefore briefly absent between claim and link. A caller retries that state only after its stop request has committed or it has joined the protected in-progress request, only within the original absolute deadline, and only for absence, `ENOENT`, or an invalid-receipt read followed immediately by a fresh absent observation; a present invalid or mismatched receipt remains a conflict. Equal roots are deduplicated, distinct Windows roots are inspected concurrently, and each new receipt temp is normalized plus verified by one bounded asynchronous ACL child before the synchronous publication so the event loop and lifecycle deadline remain responsive. Heartbeats are coalesced to one in-flight publication, recheck fatal/stopping/stopped state when dequeued and after asynchronous proof, receive their timestamp only when executed, and are canceled when a stopping or terminal transition supersedes them. The protected stop request carries one absolute 15-second deadline shared by caller and runner from request publication through every receipt and terminal proof, poll latency, ACL subprocess execution plus confirmed TERM/KILL escalation and close, exact-child termination, claim cleanup, and mandatory terminal publication. Both sides derive fifteen equal budget units and group them into non-overlapping intervals: three for publication, four for runner detection/protection/claim, two for termination, two for terminal publication, two for exact-claim cleanup, and two for caller proofs. The terminal receipt binds the request timestamps plus claim name and hash. It can become visible while cleanup still owns its interval, but callers accept it only after the exact claim is absent and the protected receipt, terminal identity, and request-absence proofs pass. If readiness is already in flight, cancellation directly supersedes it with the terminal receipt and omits the otherwise distinct intermediate `stopping` publication. The runner never creates, chmods, or ACL-repairs a missing or drifted process-state parent. Root replacement/protection drift, topology drift, or concurrent edit fails the runner closed and terminates the exact LiteLLM child before any replacement or newly mounted receipt/stop target is touched. Ready, stopping, and terminal receipts have distinct closed schemas; unknown or status-inconsistent fields fail closed. Windows changes only each new receipt file ACL, not its pre-bound parent. Any initial, heartbeat, stopping, or terminal receipt-write failure clears timers and terminates the exact child before the runner can exit; queued readiness cannot run after that failure. Only `exit`, `close`, or already-terminal child state proves termination; `error` alone never does, but a subsequent confirmed exit publishes `failed` while receipt boundaries remain safe. Every unrequested clean, nonzero, or signaled exit is recorded as failed. Status never treats freshness alone as ownership: the complete receipt structure and manifest-bound identity must match.

Start re-inventories the complete runtime, rehashes the plan- and manifest-bound Node executable, and confirms stable protected-root observations immediately before spawn. It refuses an occupied port unless a fresh receipt proves the already-running complete identity. Stop writes a closed-schema token-bound request for the runner; immediately before its synchronous claim, the runner re-verifies that bound request's identity, content, POSIX owner/mode or Windows ACL. It signals only its owned child handle, publishes `stopped` or `failed` after confirmed termination, and then removes the exact protected request claim as the completion commit. Every polled terminal receipt must preserve the initial token, runner/child, executable, arguments, configuration, host, port, and start-time identity, bind the matching request timestamps and claim hash, prove that exact claim absent, and pass the manifest/file proof again within the shared deadline before stop completion is accepted. Both terminal states complete the stop contract, and the result retains which state occurred. A concurrent request or terminal-receipt replacement is preserved, but lifecycle completion then fails and offline status reports a malformed, mismatched, or non-active residual request as process drift. A manifest with recorded process identity and no protected receipt blocks stop and rollback. Startup failure may signal only the exact `ChildProcess` handle just spawned by that call. Runner closure alone does not prove that its separately spawned LiteLLM child is gone, particularly on Windows: transaction cleanup requires runner termination plus a matching terminal receipt and exact claim-absence proof. Otherwise runtime, configuration, and credentials remain intact for manual recovery. If a start/restart succeeds but manifest persistence fails, the mutation validates the exact returned token and full identity, joins only a protected in-progress request with its embedded deadline, waits for a compensating stop while preserving caller-proof time, and restores the prior protected receipt with no-replace publication before returning the write failure. Offline status reports residual root/file and sibling-quarantine state both when no install manifest survives and alongside an in-progress rollback journal; only the verified journal itself is excluded from those residual findings.

## Proof layers

Report provider, gateway, Codex, Claude Code, and Cursor separately. Configuration is not transport proof; text is not a tool loop; gateway mocks are not live provider proof; and one client never proves another.

Before a gateway or client check can read the administrative key or accept evidence, it verifies the current manifest; every artifact and backup hash, mode, owner, or Windows ACL; the runtime tree; executable content; protected process receipt; complete process identity; and fresh `ready` heartbeat. It repeats this proof after reading the key, immediately before every selected gateway request, after each gateway/client phase, and before report publication. The immutable process boundary must remain unchanged, while expected heartbeat-only receipt replacements remain valid; the report carries the final receipt snapshot digest alongside non-secret manifest/process/config/runtime binding digests. Client evidence persists the immutable-process digest, so a restart cannot inherit proof earned by the prior process. Gateway model discovery must expose `hetzner-default`; another listener or alias cannot earn proof.

Evidence becomes stale when its model, gateway configuration epoch, executable path/version/content, client, process binding, or host boundary differs from the current verified installation. Cursor remains at `verification_required` or `blocked` unless its exact current UI and route are manually proven.
