## Interrupted setup/add-client/repair

The in-memory transaction ledger cleans up only its exact writes. Each deletion atomically moves the identity-bound target to an unpredictable same-directory quarantine path, verifies its file hash, tree digest, or process token there, rechecks both the claim and retained lock after every pre-remove boundary and immediately before deletion, and deletes only that claim. Lock release keeps its retained file proof open through that final verification and deletion. Restoration reads a hash-bound backup through a verified handle, claims the exact transaction file, and publishes only if the original name remains absent. Concurrent replacements at the original path survive. Before an external Codex-profile claim crosses a post-claim hook, its exact verified bytes are published to a protected quarantine file in managed state and removed only after successful cleanup. Therefore a parent rename cannot turn `error.recovery.path` into a pathname inside the replacement directory; CLI and offline local status point to the reachable managed claim instead. Raw post-claim filesystem failures are normalized to a stable conflict, and cleanup or lock-release failures cannot mask the original conflict. A secondary release failure adds only a stable internal failure code while preserving the primary recovery path. Offline `status`/`diagnose` also report empty managed roots, residual files/roots, sibling root/file quarantines, and residual process requests even when no manifest survives. Inspect both the original and recovery paths before any manual action. If cleanup completes, create a new plan from current state.

Never delete the lock, runtime, backup, receipt, or manifest solely because a command failed. First establish ownership from current hashes and receipt identity.

## Interrupted rollback

Before deletion, rollback atomically writes a protected journal containing the exact approved contract, non-secret credential observations, and a gateway-keyed pair-continuity HMAC. The manifest is removed last. The original approved plan resumes an interrupted journal, including after normal plan expiry; a different plan is blocked. Each resumed step recomputes the continuity proof under the mutation lock. Offline status reports `rollback_incomplete` together with any remaining managed roots, unexpected entries, or sibling quarantines; only the verified journal itself is excluded from that residual scan. Once complete, the journal is atomically replaced by a receipt recording the complete removal set and preserved credentials. Repeating that plan verifies the receipt and performs no mutation.

## Cursor

If `check --components cursor` reports `blocked`, there is no supported automated repair. Inspect only the documented current UI. Absence of a compatible base-URL control is a terminal result for that version.

## Escalation receipt

When blocked, report:

1. workflow and host boundary;
2. stable error code;
3. affected non-secret path or component;
4. current independent proof states;
5. whether state changed;
6. one safe next action.

## Native NixOS runtime limitation

The current isolated-venv installer cannot run on a native NixOS host when Python wheels require `libstdc++.so.6` outside their loader path. A real test hit this in `tokenizers`. The protected runner intentionally removes inherited loader variables, so exporting `LD_LIBRARY_PATH` is not a supported workaround. Do not weaken the runner environment or patch an unowned interpreter. Use the existing remote gateway, manual instructions in a compatible Linux environment, or an explicitly isolated Linux container. Container proof does not qualify native NixOS. A future native adapter needs declared library identities, runtime inventory and drift checks.
